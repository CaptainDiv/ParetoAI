# Entire's native Gemini CLI support was retired; we ship our own integration rather than switch Student Agents to Claude Code

> **Superseded (partially) by ADR-0005.** This integration works exactly as designed — login, enablement, hook installation, and checkpoint-branch creation are all confirmed live. What ADR-0005 found is a separate, unrelated problem: Gemini CLI's own Policy Engine denies every `run_shell_command` call under full headless automation, which blocks every edit-run-commit step regardless of this integration. The Student Agent now runs on OpenCode instead; this module stays in the repo as correct, working, documented code for the problem it actually solves.

ADR-0001 chose Gemini CLI because "Entire's checkpoint capture currently only supports... Claude Code and Gemini CLI." That was true when written, but reading `entireio/cli`'s source directly (`cmd/entire/cli/retired_gemini.go`) shows native Gemini support was since removed: the current `agent/` directory ships `antigravity`, `claudecode`, `codex`, `copilotcli`, `cursor`, `factoryaidroid`, `opencode`, `pi` — no `gemini`. `docs.entire.io`'s agent overview confirms the same list. ADR-0001's premise is corrected here rather than edited in place, per this project's own practice of standing decisions on corrected evidence (see ADR-0003).

Entire's retirement code does not just delete Gemini support outright: `retiredGeminiNameClaimed()` checks whether something named `gemini` is registered or sits on `$PATH`, and defers to it rather than stripping its hooks if so. That is a deliberate seam for exactly this situation — Entire's [Agent Integration Protocol](https://docs.entire.io/agents/agent-integration-protocol/overview) lets anyone ship an `entire-agent-<name>` executable implementing a documented command contract (`info`, `detect`, `get-session-id`, `read-session`, `read-transcript`, the `hooks` capability, etc.) and register it with `entire agent add gemini`.

We ship `entire-agent-gemini` (`pareto_ai/entire_agent_gemini.py`, with a `bin/entire-agent-gemini(.cmd)` shim — add `bin/` to `$PATH` so `entire agent add gemini` can find it) against that protocol, reverse-engineered live against installed Gemini CLI 0.63.0: its on-disk session format (`~/.gemini/tmp/<project-id>/chats/session-*.jsonl`, a header line plus either full message objects or `{"$set": ...}` merge-patches) and its native hook events (`SessionStart`, `BeforeAgent`/`AfterAgent`, `SessionEnd`, `PreCompress`, documented at geminicli.com/docs/hooks). The `hooks` capability is what makes checkpoint capture real; several of Entire's other optional capabilities (`transcript_analyzer`, `token_calculator`, `transcript_preparer`, `text_generator`, `subagent_aware_extractor`) are deliberately not implemented yet — Entire degrades gracefully without them, and their absence is legible in `entire-agent-gemini info`'s declared `capabilities`, which is the ADR-0002 bar: visible, not hidden.

## Considered Options

- **Switch Student Agents to Claude Code**, which Entire does support natively — rejected for now: ADR-0001 already weighed this and rejected it over separate pay-as-you-go Anthropic spend; nothing about that tradeoff changed, so revisiting it wasn't the fix for a documentation/retirement gap.
- **Fake a Checkpoint-shaped record ourselves** (what ADR-0001 already rejected as "not a real Entire integration") — rejected, now for an additional reason: Entire's own retirement path explicitly anticipates and welcomes a real external integration, so there's a sanctioned alternative that isn't faking it.
- **Implement the full protocol, every optional capability** — rejected for this ticket: the required commands plus `hooks` are what the acceptance criteria need (a real, verifiable Checkpoint); the rest would be scope with no load-bearing use yet.

## Consequences

- `entire-agent-gemini` must be on `$PATH` and registered (`entire agent add gemini`) before a Student Agent Attempt can produce a real Checkpoint. `entire login` is a one-time action tied to the user's own Entire account and cannot be scripted by an agent.
- The session-directory lookup used by `get-session-dir`/`resolve-session-file` depends on Gemini CLI's project registry (`~/.gemini/projects.json`), which is undocumented and could change across Gemini CLI releases; the hook-driven capture path (the one that matters for checkpoint capture) does not depend on it, since Gemini CLI hands `transcript_path` directly in each hook's stdin payload.
- Hooks install into the **user**-level `~/.gemini/settings.json`, not a repo-level `.gemini/settings.json` — confirmed live against gemini-cli 0.63.0 that a repo-level `hooks` key never reaches the live hook registry at all (`Hook registry initialized with 0 hook entries`; gemini-cli's own bundled source has a `// TODO: loading of hooks based on workspace trust` sitting at the exact call site that would need to read it). A user-level key does load and does attempt execution (confirmed via a real "Expanding hook command" / "Created execution plan" trace). The consequence: installing this integration makes Entire capture *every* Gemini CLI session on the machine, not just ones inside a repo where `entire enable` has run — breadth we did not choose, imposed by Gemini CLI's own hook scoping. This is a real limitation, not a correctness bug: Entire's main binary (`entire hooks gemini <verb>`) is what actually runs on each firing, and is free to no-op for a session it holds no record of.
- External-agent discovery (`entire agent add <name>` / `entire agent list`) is gated behind an `external_agents` setting (`cmd/entire/cli/agent/external/discovery.go`) that nothing sets automatically — `entire agent add gemini` answers "Unknown agent" until it's on. The actual unlock is `entire enable --agent gemini`: its `--agent` flag calls `DiscoverAndRegisterNamedAlways`, which explicitly bypasses that setting for one named, explicit selection. Confirmed live: `entire enable --agent gemini --checkpoint-backend branch` installed exactly the 5 hook entries `with_managed_hooks` is supposed to produce into `~/.gemini/settings.json`, and created a real `entire/checkpoints/v1` orphan ref in the target repo.
- Entire's default checkpoint storage is no longer the `entire/checkpoints/v1` branch this project's CONTEXT.md names — `entire enable --help` (0.11.4) shows `--checkpoint-backend` defaulting to `refs` (one git ref per checkpoint), with `branch` ("legacy shared `entire/checkpoints/v1` branch") now opt-in. `enable_entire` must pass `--checkpoint-backend branch` explicitly for issue #6's acceptance criterion to mean anything.
- The hang reported in the first pass turned out to be specific to this project's own sandboxed tool environment, not Gemini CLI, Entire, or this integration: run directly by a person in a real terminal, `gemini -p ... --skip-trust` completed three separate times inside the repo where this integration is enabled (one full success, two fast failures on auth/quota before a turn even started) — none hung. Only the agent's own sandboxed command execution reproduced the hang, through two independent invocation paths that both nested Gemini's own child-process spawn three or more processes deep inside that sandbox's piping/timeout layer; a real terminal does not have that extra layer.
- Still open, now blocked by a chain of unrelated external hiccups (quota, then a retired model name, then a transient 503) rather than by any hang: no run yet has both (a) happened from inside the Entire-enabled repo and (b) completed a full turn that edits a file and commits, so `entire checkpoint list` has not yet been observed showing a real Checkpoint. Confirming that is the one thing standing between this integration and issue #6's AC1 being verified rather than merely plausible — not a blocker on other work, since everything else about the integration (login, enablement, hook installation, the checkpoint branch, Entire's own dispatch into it, Gemini CLI running without hanging) is already confirmed.
- `--skip-trust` and Gemini CLI's Policy Engine are two different gates, confirmed live: `--yolo` auto-approves tool calls via a high-priority Policy Engine rule ("In yolo mode, a high-priority rule allows all tools" — geminicli.com/docs/reference/policy-engine), but `--skip-trust` only skips the interactive trust *prompt* — it does not grant the Policy Engine's actual trust. The result: `gemini -p ... --skip-trust --yolo` still denies every `run_shell_command` call with "Tool execution denied by policy", which blocks every edit-run-commit step an Attempt needs. `GEMINI_CLI_TRUST_WORKSPACE=true` is what actually grants that trust. `student_agent.run_gemini_attempt` sets it.
