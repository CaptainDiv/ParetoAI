# A Source is a measure of market demand, not reference documentation

The Analyst originally ranked skills by how many canonical documentation pages mentioned them (ethereum.org, the Solidity docs, OpenZeppelin Contracts). Run live, that produced a table where **45 of 45 entries tied at frequency 1**, and even after an LLM pass merging differently-worded names only 7 of 40 reached 2 — because reference documentation *partitions* a subject rather than surveying it. `ERC-20 standard` is absent from the Solidity security page not because tokens don't matter but because that page is about something else, so counting its absence as a zero is a category error. Worse, it made the ranking circular: a skill's score was decided by how many of the hand-picked pages happened to cover its sub-area, so including three security-ish Sources made security topics score 2 — the "demand signal" was a readback of the source list a human chose. So **Source** is now defined as a published measure of market demand (occupational task data, developer survey results, certification exam objectives), and the ranked quantity as **Demand Weight** rather than a frequency. That is the measure user story 1 actually asks for — "the ~20% of material that covers most real-world demand" — and the kind of source the original spec listed before the implementation drifted to documentation because documentation was easier to fetch.

## Considered Options

- **Keep documentation Sources, count how many mention each skill** — rejected: demonstrably flat and circular, per above. It is by far the easiest to fetch, which is exactly why the implementation drifted here; the convenience is the trap.
- **Keep documentation Sources, rank by prominence within the corpus** (headings, sections, depth rather than source count) — rejected: it reads as a demand signal while really measuring how verbose a page is, letting one long reference page outvote a genuinely important topic. It would have required no new sources, which was its only real appeal.

## Consequences

- Reference documentation is **not** a Source, however authoritative. A future reader will reasonably want to add the Solidity docs back — that reintroduces the circularity above. Documentation's proper place is as a Module's Resource, which is where the Curriculum agent already uses it.
- The weighting signal comes from **O*NET 15-1299.07 (Blockchain Engineers)**, whose task and work-activity lists carry numeric 0–100 importance ratings, plus the **OWASP Smart Contract Top 10**, whose ordering is derived from a practitioner survey and incident data. Certification exam objectives contribute decomposition but no weighting: none of the smart-contract certifiers publishes per-domain percentages, and the largest forbids automated fetching in its terms. The Stack Overflow survey contributes nothing — Solidity is absent from the 2025 technology page entirely.
- **O*NET's weights are coarse exactly where the Curriculum needs them fine.** Its tasks are occupation-level ("Test the security and performance of blockchain infrastructures"), not Solidity-level, so the only real numeric signal does not decompose to the granularity a Module wants.
- **The security-bias trap is this ADR's own hazard in demand-shaped clothing.** OWASP Top 10, OWASP SCWE and EEA EthTrust are all security documents; adopting them as three Sources would make security rank high *because three security Sources were chosen* — precisely the circularity diagnosed above for documentation. Count the OWASP family as one signal.
- `PAGE_TEXT_CHARS` is now a **content** decision, not just a token budget: a global 5000-char cap is what excludes the EthTrust checklist, whose first requirement sits at offset ~5,868. Per-Source caps serve this definition better than one global cap.
- `ParetoEntry.frequency` is misnamed under this decision and still computes `len(sources)`. The code lags the model until #11 lands.

## Correction (2026-10-10)

As first written, this ADR asserted that "O*NET has no smart-contract occupation" and that certification exam objectives were "the one demand Source that both decomposes into sub-skills and publishes weightings, so they carry most of the load for the MVP". Both claims were reasoned rather than checked, and both were wrong: O*NET added **15-1299.07 — Blockchain Engineers** (updated 2026, CC BY 4.0, `robots.txt` permits `/link/`), and no smart-contract certifier publishes exam weightings at all.

The decision is unchanged, and the correction strengthens rather than weakens it: occupational task data with per-item importance ratings is the first example the `Source` definition gives, and it turns out to exist for this Target Skill. What changed is which Sources carry the load. Evidence, with fetch verification and measured offsets, is in [`docs/research/demand-sources-for-smart-contract-development.md`](../research/demand-sources-for-smart-contract-development.md).
