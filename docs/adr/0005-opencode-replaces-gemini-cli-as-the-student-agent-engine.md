# The Student Agent runs on OpenCode, not Gemini CLI; the model comes from neatHack's own LiteLLM gateway, not a provider's free tier

ADR-0004's `entire-agent-gemini` integration genuinely works — confirmed live: `entire login`, `entire enable --agent gemini`, correct hook installation into `~/.gemini/settings.json`, a real `entire/checkpoints/v1` branch, and a real commit. What it could not get past is Gemini CLI's own Policy Engine: `run_shell_command` is denied under full headless automation no matter the combination tried (`--skip-trust`, `--yolo`, `GEMINI_CLI_TRUST_WORKSPACE=true`, an explicit `~/.gemini/policies/*.toml` allow rule at priority 999) — confirmed by hitting the identical "Tool execution denied by policy" error in two independent environments (this agent's sandbox and the project owner's own terminal), which rules out environment-specific flakiness as the explanation. Every edit-run-commit step an Attempt needs depends on `run_shell_command`, so this blocks the ticket outright, not just one test run.

We switched the Student Agent's engine to OpenCode instead of continuing to chase Gemini CLI's Policy Engine, on the strength of a verified precedent: Kedge, another real neatHack submission (github.com/faroukobayanju/kedge), solved the identical problem — a headless coding agent that must produce a real commit with a real Entire Checkpoint — using OpenCode with no equivalent shell-permission gate. Entire supports OpenCode as a built-in agent integration (`entire enable --agent opencode` registers and enables it in one call, no custom plugin required, unlike Gemini CLI post-retirement).

The model behind OpenCode is **not** a provider's free tier. The first attempt used Groq (this project already holds a `GROQ_API_KEY`), and every call — on both `openai/gpt-oss-20b` and `openai/gpt-oss-120b` — failed with "Request too large... Limit 8000 TPM" before the task was ever attempted: OpenCode's own baseline tool-definition overhead (~14,000 tokens) exceeds Groq's free "on_demand" tier's organization-wide token-per-minute cap, regardless of which Groq model is chosen. Kedge's own config pointed at `https://litellm.vision.aivar.app/v1` — **neatHack's own LiteLLM gateway**, confirmed against the hackathon's own published pages (neatlogs.com/hackathon and /hackathon/models), which grants every checked-in team a $20 shared budget across seven real models (`nova-micro`, `nova-lite`, `nova-pro`, `nova-2-lite`, `claude-haiku`, `claude-sonnet-4.6`, `claude-opus-4.6`) via an OpenAI-compatible API — no tiny free-tier cap, and no cost to the project beyond the hackathon's own allowance. `opencode.json` at the repo root declares this provider; `LITELLM_API_KEY` lives in `.env` (gitignored).

Two configuration details cost real debugging time and are recorded so they aren't rediscovered:

- Every model entry in `opencode.json` needs an explicit `limit.output` (and `limit.context`). Without it, OpenCode defaults to requesting a larger output-token cap than the gateway's underlying models (Bedrock Nova) actually allow, and every call fails with "exceeds the model limit of 10000" — a different, model-specific error from the Groq TPM one, easy to mistake for the same problem.
- `run_opencode_attempt` passes `stdin=subprocess.DEVNULL` and sets `PWD` explicitly in the subprocess environment. Both came from Kedge's own setup, confirmed live: an inherited stdin stops OpenCode from loading Entire's plugin at all (silently — no error, just no Checkpoint), and OpenCode resolves its project and plugins from `PWD`, not from the subprocess's working-directory argument alone.

OpenCode is pinned to `1.18.35`, not the `1.19.0` that `npm install -g opencode-ai` installs by default — Kedge's setup script pins the same version with the same reasoning: a newer OpenCode's plugin API rejects Entire's generated plugin ("Plugin must export a default definition"), which would mean zero Checkpoints captured with no clear error pointing at the version mismatch.

## Considered Options

- **Keep fighting Gemini CLI's Policy Engine** — rejected: every fix attempted (workspace trust, yolo, an explicit policy file at increasing priority) hit a different wall, and the same exact failure reproduced identically in two independent environments, which is strong evidence this is Gemini CLI's actual headless-automation behavior rather than a configuration mistake we hadn't found yet.
- **Pay for Groq's Dev Tier to raise the TPM cap** — rejected: the pricing information found online conflicted across sources badly enough to be unusable (no fixed price, vs. ~$5/month, vs. pay-as-you-go), and the hackathon's own LiteLLM gateway was already a known-working, zero-incremental-cost alternative once Kedge's precedent surfaced.
- **Switch to Claude Code** (ADR-0001's original alternative) — rejected again: nothing about the pay-as-you-go cost tradeoff that ADR-0001 and ADR-0004 already weighed has changed, and OpenCode solves the actual problem (a real headless commit with a real Checkpoint, confirmed live) without that tradeoff.

## Consequences

- `pareto_ai/entire_agent_gemini.py` and `bin/entire-agent-gemini(.cmd)` (ADR-0004) are no longer part of the active Student Agent pipeline. They stay in the repo: real, tested, working code that correctly solves the problem it set out to solve (restoring Entire's retired Gemini CLI support) — the Student Agent just doesn't need that problem solved anymore, since it isn't running Gemini CLI. Deleting correct, documented work because the surrounding plan changed would erase the evidence of what was actually tried and why, which matters for this hackathon's own "building in public" and "failure recovery" evidence requirements.
- The Student Agent now depends on the neatHack hackathon's $20 shared LiteLLM budget rather than a provider the project controls independently. That budget is time-boxed (30 days from grant) and shared across the whole team — a concern for sustained use beyond the hackathon, not for building and demoing the MVP.
- Verified live end-to-end on 2026-10-11: a real edit (`hello.txt`), a real commit, and a real Entire Checkpoint (`entire checkpoint list` showing `checkpoints: 1`, `entire checkpoint explain` showing the full transcript) linked to it on `entire/checkpoints/v1`. This is issue #6's AC1 confirmed, not merely plausible.
